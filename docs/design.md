# 우리동네GS 추천 온톨로지 설계

대체재 · 보완재 · 트렌드 · 콤보 추천 / 1차 범위: 과자 43 · 라면 18 (시드)

## 1. 목표

우리동네GS 상품 추천을 온톨로지 그래프DB로 만든다. 추천은 네 가지다.

| 추천 | 질문 | 그래프 표현 |
|---|---|---|
| 대체재 | 이게 없으면 뭘 사면 되나 | `(:Product)-[:SUBSTITUTE {strength}]->(:Product)` |
| 보완재 | 이거랑 같이 뭘 사면 좋나 | `(:Product)-[:COMPLEMENT {strength, reason}]->(:Product)` |
| 콤보 | 이 상황(TPO)에 뭘 묶어 사나 | `(:Combo)-[:FOR]->(:Scene)-[:AT]->(:TPO)`, `(:Combo)-[:INCLUDES {role}]->(:Product)` |
| 트렌드 | 요즘 뭐가 뜨나 | `(:Product)-[:IN_TREND {score}]->(:Trend {period})` |

핵심은 **튀는 추천 방지**다. 유사도 점수만으로는 짜파게티의 대체재로 비빔면이 나오고, 젤리 대신 껌이 나온다.
그래서 TPO와 상품간·규격·속성·아이덴티티 정책을 온톨로지로 정의하고, 정책을 통과한 것만 추천 간선으로 만든다.

## 2. 전체 흐름 — 속성 증강 파이프라인

```
원본 상품 (이름·카테고리·속성 표기)
  ① 정규화      동의어 흡수(청양→매운맛), 처음 보는 값은 비우고 후보 큐로
  ② 속성 부여    뎁스1 정체성 → 뎁스2 감각 → 뎁스3 상황·가치 → 뎁스4 세부
  ③ TPO 추론    속성 → 시간·장소·날씨 (규칙 기반, 상품마다 손으로 찍지 않음)
  ④ 아이덴티티   카테고리 2단계(과자) / 조리형태(라면)
  ⑤ 점수        뎁스별 가중 유사도 (sweep으로 뎁스·가중치 결정)
  ⑥ 정책 필터    상품간·규격·속성·아이덴티티·TPO 하드 조건
  ⑦ 간선 강도    검수 결과 반영 (O=바닥 0.5, X=삭제, 미검수=20% 할인)
  ⑧ 콤보        장면(TPO)별 슬롯 채우기, 정체성 중복·예산 초과 제외
  ⑨ 그래프 적재  Neo4j (out/graph.cypher)
  ⑩ 인간 검수    out/audit.md · review/queue.csv → ⑤로 돌아감
```

## 3. 텍소노미

카테고리 트리 34노드. 모든 노드에 정의가 있다(`taxonomy/categories.yaml`).

| 대분류 | 중분류 | 정의(요약) |
|---|---|---|
| 과자 SNK | 칩(생감자·성형·곡물), 팽화·압출, 소맥 튀김, 견과 | 조리 없이 먹는 상온 스낵 |
| 비스킷·쿠키 BIS | 크래커, 쿠키, 웨하스, 스틱, 샌드, 슈볼 | 오븐에 구운 과자 |
| 파이·케이크 CAKE | 초코 코팅, 비코팅 | 부드러운 시트 + 크림, 개별포장 |
| 초콜릿 CHO | 판·바 | 카카오 주성분, 녹는 식감 |
| 캔디·젤리·껌 CDY | 젤리, 츄잉캔디, 껌 | 당류를 굳히거나 졸인 과자 |
| 라면 RMN | 국물(얼큰·순한·해물·우동), 국물없음(짜장·볶음·비빔) | 물·열로 조리하는 즉석 면, 식사대용 |

## 4. 속성과 뎁스 (속성 증강)

속성 17개, 값마다 정의와 동의어가 있다(`taxonomy/schema.yaml`).

| 뎁스 | 의미 | 공통 | 과자 전용 | 라면 전용 |
|---|---|---|---|---|
| 1 정체성 | 무엇인가 | 카테고리, 유탕여부 | 주원료, 제조방식 | 포장형태, 조리형태 |
| 2 감각 | 어떤 맛·식감 | 맛계열, 맵기 | 식감, 형태 | 국물베이스, 면 |
| 3 상황·가치 | 언제·얼마에 | 가격대, 용량, 섭취상황 | | |
| 4 세부 | 누가 | 주타깃, 제조사 | | |

뎁스는 추천 가중치를 돌려서 정한다. 뎁스 1~4마다 뎁스별 가중치 배수(0.25/0.5/1/2)를 전부 돌려
검수 정답셋으로 AUC(대체 O가 X보다 높게 나오는 비율)와 MRR(대체 O 후보의 순위)을 잰다.

| 사용 뎁스 | AUC | MRR | 종합 |
|---|---|---|---|
| ≤1 | 0.957 | 0.888 | 0.923 |
| ≤2 | 0.980 | 0.902 | 0.941 |
| **≤3 (선택)** | **0.988** | **0.917** | **0.952** |
| ≤4 | 0.990 | 0.902 | 0.946 |

뎁스4(제조사·타깃)를 넣으면 같은 제조사끼리 묶이면서 순위가 오히려 나빠진다. 현재는 뎁스3까지 쓴다.
정답셋이 늘면 결과가 바뀔 수 있으므로 검수 후마다 다시 돌린다.

## 5. 과자 vs 라면

| 관점 | 과자 | 라면 |
|---|---|---|
| 공통 축 | 맛계열·맵기·가격대·용량·섭취상황·제조사 | 같음 |
| 목적 | 간식·디저트·안주 | 식사대용 |
| 정체성을 가르는 것 | 제조방식·식감·형태 | 조리형태·국물베이스 |
| 조리 | 개봉 즉시 | 포장형태가 조리 장소를 결정(봉지=냄비, 컵=뜨거운 물) |
| 주원료 | 다양 → 판별력 있음 | 거의 밀가루 → 속성에서 제외 |
| 대체 범위 | 같은 대분류·같은 목적 | 같은 조리형태만 (국물↔짜장은 대체가 아니라 보완: 짜파구리) |

공통 축은 카테고리를 넘는 보완재·콤보에, 고유 축은 같은 카테고리 안의 대체재 판단에 쓴다.

## 6. 정책 (튀는 추천 방지)

`ontology/policy.yaml`. 정책은 하드 조건이다. 점수가 아무리 높아도 어기면 간선을 만들지 않는다.

| 정책 | 정의 | 과자 | 라면 |
|---|---|---|---|
| 아이덴티티 | 손님이 '같은 종류'라고 느끼는 단위 | 카테고리 2단계 | 조리형태 |
| 상품간 — 대체재 | 같은 욕구를 채우는가 | 같은 대분류 + 섭취상황 겹침 | 같은 조리형태 + 섭취상황 겹침 |
| 규격 | 대체재끼리 허용되는 차이 | 가격대·용량 1단계, 맵기 2단계 이내 | 같음 |
| 상품간 — 보완재 | 같이 사면 가치가 커지는가 | 다른 정체성 + 시간대 겹침 | 같음 |
| 콤보 | 한 장면의 묶음 | 장면 TPO 적합 + 정체성 중복 없음 + 예산 이내 | 같음 |
| 트렌드 | 뜨는 상품 | 점수 0.3 이상 + 위 정책 통과 | 같음 |

정책이 실제로 막은 예 (시드 기준 7건):

| 추천 후보 | 유사도 | 막은 정책 |
|---|---|---|
| 짜파게티 → 팔도비빔면 | 0.564 | 아이덴티티: 조리형태 다름 |
| 불닭볶음면 → 팔도비빔면 | 0.578 | 아이덴티티 + 규격(맵기 극강→약) |
| 하리보 → 자일리톨 껌 | 0.678 | 상품간: 섭취상황 겹침 없음(간식 vs 입가심) |
| 참크래커 → 버터링 | 0.698 | 규격: 가격대 2단계 차이 |

검수에서 O를 받았는데 정책에 걸리면 '정책 충돌'로 따로 보고한다. 정책이 틀렸는지 검수가 틀렸는지 사람이 정한다.

## 7. TPO

`ontology/tpo.yaml`. 상품마다 TPO를 찍지 않고 속성에서 추론한다. 새 상품도 속성만 채우면 TPO가 따라온다.

| 차원 | 값 |
|---|---|
| 시간대 | 아침, 점심, 오후, 저녁, 심야 |
| 장소 | 집, 사무실·학교, 야외·캠핑, 이동중 |
| 날씨 | 더움, 추움, 비 |
| 섭취상황 | 간식, 술안주, 식사대용, 야식, 디저트, 나눔, 입가심, 해장 (속성) |

추론 규칙 예:

- 섭취상황=술안주 → 저녁·심야, 집·야외
- 포장형태=봉지 → 야외 가능, **사무실·이동중 제외** (냄비가 없다)
- 조리형태=국물 → 추움·비, **더움 제외** / 비빔 → 더움
- 식감=녹는(초콜릿) → **더움 제외**

장면(scene) 6개: 심야 혼술·야식, 사무실 점심 컵라면, 오후 사무실 나눔, 캠핑 저녁, 더운 날 점심, 비 오는 날 저녁.

## 8. 간선 강도

| 관계 | 강도 |
|---|---|
| 대체 — 검수 O | 0.5 + 0.5 × 유사도 (바닥 0.5) |
| 대체 — 검수 X | 간선 없음 |
| 대체 — 미검수 | 0.8 × 유사도 (상품당 상위 5, 유사도 0.55 이상) |
| 보완 — 지정 조합 | 사람이 정한 값 (짜파구리 0.9) |
| 보완 — 속성 규칙 | 0.25~0.35 (가설, 검수로 올림) |
| 콤보 궁합 | 상품쌍 보완 강도 평균, 보완 간선이 없으면 시간대 겹침 × 0.3 |

## 9. 새 상품에 없는 속성이 들어왔을 때

1. **동의어 흡수**: 기존 값의 다른 표기면 synonyms에 추가 (청양 → 매운맛)
2. **비워 두기**: 흡수가 안 되면 그 값은 점수에서 뺀다. 가장 가까운 값에 억지로 붙이지 않는다 (틀린 간선이 생기는 것보다 간선이 약해지는 게 낫다)
3. **후보 큐**: `review/new_values.csv`에서 사람이 synonym / new / drop 판단. new는 정의를 함께 써야 등록된다
4. **승격 기준**: 서로 다른 상품 3개 이상에서 나오거나 추천 품질에 영향이 있을 때
5. **결측**: 해당 속성만 빼고 가중치 재정규화. 비교 가능 가중치의 70% 미만이면 그 비율만큼 감점
6. **새 축·새 카테고리**: 정의와 함께 추가. 새 축은 뎁스4로 시작해 sweep에서 기여하면 올린다

## 10. 인간 검수 루프

```
validate → sweep → review export → (사람: queue.csv에 O/X) → review import → sweep → graph → audit.md 확인
```

- 정책이 막은 쌍은 검수 큐에 올리지 않는다 (사람 시간을 아낀다)
- X가 많이 나오면 스키마가 그 차이를 못 잡는다는 뜻이므로 속성·정책을 고치고 루프를 다시 돈다
- `out/audit.md`: 정책 충돌, 장면별 콤보, 상품별 대체재 상위 3, 정책이 막은 추천, 처음 보는 값

## 11. 그래프 스키마

| 노드 | 의미 |
|---|---|
| Product | 상품 (identity 속성 포함) |
| Category | 카테고리 트리 노드 |
| Attribute / AttrValue | 속성 축 / 값 (정의 포함) |
| TPO | 시간·장소·날씨 값 |
| Scene / Combo | 콤보 장면 / 콤보 |
| Policy | 정책 정의 |
| Trend | 기간 |

| 관계 | 의미 |
|---|---|
| IN_CATEGORY, SUBCATEGORY_OF | 분류 |
| HAS_ATTR, HAS_VALUE | 속성 |
| FITS / AVOIDS | 상품이 맞는 / 피하는 TPO |
| SUBSTITUTE, COMPLEMENT | 추천 간선 (strength) |
| AT, FOR, INCLUDES | 장면 TPO, 콤보 소속, 콤보 구성 |
| IN_TREND | 트렌드 |
